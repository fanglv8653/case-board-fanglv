v0.8.3 只处理会导致应用无法启动、设备同步无法收敛或本地绑定事务失败的数据安全缺陷，不混入需要额外产品决策的后台计费功能。

2. 将“每月 27 日至次月 26 日、赠送 3500 积分”固化为全局产品规则；

### V083-M1｜数据库迁移谱系与启动恢复

目标：任何未知谱系均先失败关闭，原数据库不被改写，应用给出可操作提示而非 panic 闪退。

#### 实现要求

1. 将迁移处理拆成“只读预检 → 分类 → 允许的兼容动作 → sqlx migrate”四步；
2. 禁止仅凭迁移编号覆盖 checksum；白名单至少包含“版本号＋已知旧 checksum＋当前 checksum＋预期 schema sentinel”；
3. 对未知 checksum、未知已应用迁移、失败迁移行、关键表/列/触发器缺失返回稳定错误码；
4. 同时收紧 `set_ignore_missing(true)`：默认不得忽略未知已应用迁移；只有预检确认所有缺失版本均属于明确白名单时才允许继续；
5. 对迁移 49、51、58—62 建立关键 schema sentinel，至少核验相关表、列、外键和触发器；
6. 未知或不兼容路径必须在任何 checksum、schema 和业务数据写入前退出；
7. `DbError` 增加结构化兼容错误，Tauri `setup` 捕获后使用原生对话框显示错误码、数据库位置、备份建议和退出操作；不得依赖 WebView 已启动；
8. 无业务数据的异常库只提供“先备份，再由用户确认创建新库”的恢复说明，不自动删除、覆盖、重命名或重建；有业务数据时只允许隔离审计和受控迁移；
9. 兼容白名单动作必须记录不含业务数据的本地诊断日志。

#### 验收标准

- 当前 0.8.2 正常数据库可升级到 v0.8.3 最大迁移，`quick_check=ok`、`foreign_key_check` 为空；
- 未知 checksum、未知迁移版本和 sentinel 缺失均返回对应稳定错误码；
- 不兼容数据库执行前后 `_sqlx_migrations`、schema 和业务表指纹一致；
- 笔记本故障形状不再触发无提示闪退；
- 全新库 0→最大迁移正常；
- Windows 启动/升级脚本纳入上述数据库夹具。

### V083-S1｜设备同步循环引用、分包与隔离生命周期

目标：真实形状基线能够原子导入；确定性失败不会无限重试、无限新增隔离或被报告为同步成功。

#### 实现要求

1. 在解密和完整性校验通过后，先分析事件内实体依赖，再进入写事务；
2. 对循环引用实施两阶段写入：案件首次 upsert 安全延后 `judge_id`，联系人落库后在同一事务内补写并再次校验；禁止关闭外键约束；
3. 导出端增加依赖感知排序和原子分组，案件与被引用联系人不得因 500 条边界被拆成无法应用的事件；
4. 若合法基线超过单事件容量，必须按依赖闭包分包；无法安全分包时在写 NAS 事件前失败，不得生成接收端必然无法应用的包；
5. 被引用实体既不在当前依赖闭包、也不在接收端时，整包回滚并返回 `SYNC_PACKAGE_DEPENDENCY_MISSING`；
6. `device_sync_quarantine` 增加生命周期：`active/resolved`、首次时间、最近时间、重试次数、解决时间和最后错误码；同一 `group_id + source_path + reason_code` 的活动隔离只更新计数；
7. 界面“隔离数”只统计 `active`，历史已解决记录保留审计，不物理删除；
8. 确定性包错误首次隔离后自动暂停同步组并返回 `SYNC_GROUP_AUTO_PAUSED`；修复后由用户明确恢复和重试；
9. 有隔离时 `sync_once`、审计结果和界面必须显示失败/已暂停，不得写成 `succeeded` 或只显示“手动双向同步完成”；
10. 区分“最近尝试时间”和“最近业务同步成功时间”，隔离失败不得推进成功时间；
11. 隔离详情只展示设备、序号、源文件名、错误码和安全摘要，不展示业务正文、密钥或解密载荷。

#### 测试矩阵

- 空接收端＋非空 `judge_id`；
- 联系人反向引用案件；
- 多案件共用/不共用联系人；
- 500、501 和大于 1000 条实体；
- 依赖闭包位于同包、跨包及真正缺失；
- 失败整包回滚；
- 同一失败包重复调度只增加 `retry_count`；
- 自动暂停后后台调度不再重试；
- 修复后明确恢复、重放、解决隔离；
- 双向两轮同步幂等，冲突 0、活动隔离 0、`foreign_key_check` 0、`quick_check=ok`。

### V083-F1｜飞书孤立绑定本地修复

目标：删除案件或遇到历史孤立绑定时，本地预演和解绑事务可恢复，不误报权限问题，不触发任何自动飞书写入。

#### 实现要求

1. 案件删除事务只在本地归档关联的 active link、恢复 inbox 为 `pending_binding`、设置 `auto_bind_suppressed=1` 并 supersede 待处理候选；
2. 上述动作不得调用飞书网络接口，不删除飞书记录，不修改其他案件业务字段；
3. 拉取前识别孤立绑定，单条隔离并继续处理其他有效案件，不让整批预演回滚；
4. 解绑审计对已删除案件使用 `NULL` 或不受外键约束的历史快照，不再写入失效 `previous_case_id`；
5. 预演显示“本地案件已删除”，禁用“采用飞书/写回飞书”，只保留解除绑定；
6. 前端按 `FEISHU_ORPHAN_BINDING`、`FEISHU_REVIEW_NOT_FOUND` 等稳定错误码显示准确原因，不按中文文本分类错误。

#### 验收标准

- 案件删除、孤立拉取、孤立解绑、重新绑定均有回归测试；
- 一个孤立绑定不影响其他有效案件生成预演；
- `foreign_key_check` 为空、审计记录可追溯；
- 网络调用断言为 0；
- 飞书真实验证只使用隔离测试 Base，并继续遵守“后台只生成预演、任何写回均由用户明确触发”。

## 四、开发安全边界

1. 所有数据库测试只使用构造库、在线一致性副本或已确认可丢弃的隔离库；
2. 不直接修改两台正式数据库、当前 NAS 事件目录、同步组、成员密钥或隔离记录；
3. 正式设备同步继续保持暂停，恢复前必须重新只读确认状态；
4. 不读取、输出或写入 API Key、Token、案件正文、settings.json、解密事件载荷；
5. 飞书测试只使用隔离测试 Base，任何本地修复不得隐式触发飞书网络写入；
6. 保留脏工作树和既有未跟踪证据，不执行 reset、checkout 覆盖或清理；
7. 同一仓库构建串行执行；Windows Cargo 增量缓存占用时仅对当前进程设置 `CARGO_INCREMENTAL=0`；
8. 计划、契约、测试证据和阶段结果写入 v0.8.3 工作树及项目主日志。
