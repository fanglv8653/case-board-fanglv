## 返工 C 实现

### 1. NAS 原子不覆盖与耐久边界

- 临时文件使用 `create_new` 创建，完整写入后执行文件 `sync_all`。
- Windows 发布调用 `MoveFileExW`，只启用 `MOVEFILE_WRITE_THROUGH`，不启用 replace 标志；目标已存在时不会被覆盖。
- 非 Windows 发布使用同文件系统 `hard_link(temp, target)` 获得原子 no-replace 语义，发布后清理本线程临时文件并同步父目录。
- 发布冲突后只读取胜者：字节完全一致视为幂等成功，字节不同返回脱敏 `SYNC_INTEGRITY`；任何路径都不删除或覆盖胜者文件。
- 真实线程屏障测试连续竞争不同字节和相同字节：不同字节始终一胜一拒且目标是完整候选；相同字节双方均幂等成功。

### 2. 持久化草稿密码学校验

- 恢复 prepared draft 时，先校验 group、local device、sequence、key epoch、前序 manifest hash、operation IDs/顺序/指纹及信封头绑定。
- 随后从可信本机成员记录读取签名公钥，分别对 event 与 manifest 调用 `open`：覆盖 Base64、nonce、真实 ciphertext hash、Ed25519 签名与 AES-GCM 认证。
- event 明文重新反序列化为 `SyncOperation`，核对操作 ID 顺序与指纹；manifest 明文重新反序列化并核对 group/device/sequence/event hash/previous hash。
- 缺少可信本机签名公钥稳定映射为 `SYNC_INTEGRITY`，不泄露裸数据库错误。
- 无 prepared draft 时先完成 planner；只有形成或加载 draft 后才读取凭据，保证确定性 planner 错误仍按原契约隔离和自动暂停。
- event 与 manifest 各自覆盖 ciphertext、ciphertext hash、signature、nonce、protocol、payload kind、group、device、sequence、epoch，共 20 个篡改子案例；全部在 NAS 写入和数据库推进前失败。

### 3. 生产导出编排故障注入

- `export_pending` 与测试入口共用同一 `export_pending_inner` 产品编排，测试只注入临时密钥材料和故障点，不再手工拼接 prepare/publish/finalize。
- 故障点覆盖 manifest 发布后、event 发布后、SQLite CAS 后回滚。
- 每个故障点均验证 draft、outbox、sequence 未错误推进，并通过再次调用同一生产编排完成恢复。
- 501 项两包场景验证：第一包 500 项完成，第二包在 manifest 后中断；重试只恢复第二包剩余 1 项，不重新生成或推进第一包。

### 4. `capture_sequence` 多连接并发

- `capture_dirty_entities` 与 `enqueue_operation` 在读取当前 revision/MAX 及分配新序列前，均在事务内对同步组执行 no-op update，取得 SQLite 组级写锁。
- 两个独立 SQLite 连接并发 enqueue 并提交，最终序列严格为 `[1, 2]`，无重复、无回退、无锁错误。
- 基线仍只建立 dirty marker；后续捕获继续使用同一分配器和锁边界。

### 5. Windows 测试清理稳定性

- 完整契约套件首次运行时，业务断言均已通过，但一个文件型并发测试在 pool 关闭后清理临时 SQLite 文件时遇到 Windows OS 32 短暂占用。
- 两个文件型并发测试统一改为有限重试清理：最多 20 次、每次间隔 25ms；超时仍显式失败，不吞掉持久占用错误。
- 修正后完整契约与 Windows 全量均稳定通过。
