## 一、完成结果

1. 案件删除改为单一数据库事务：逐条校验活动绑定与 inbox，统一失效字段/明细候选及冲突，归档 link、恢复并抑制 inbox、写 NULL 旧案件外键的解绑审计，最后删除案件；任一关联缺失即整体回滚。
2. 拉取事务会先隔离当前表内的孤立活动绑定；孤立项不再拖垮同批有效案件，run 以 `partial + FEISHU_ORPHAN_BINDING` 完成，并记录孤立数量。
3. 解绑、重绑和删除共用同一候选失效逻辑；重用 archived link 前再次失效旧候选，旧 field/entity/conflict 不再具有跨案件执行权。
4. 字段和明细网络动作统一经过生产编排 helper：先分类候选/绑定/案件状态并校验本地快照，再允许执行注入的网络闭包。稳定分类为：
   - 候选不存在：`FEISHU_REVIEW_NOT_FOUND`
   - 候选已处理、link 已归档或绑定归属变化：`FEISHU_REVIEW_ALREADY_RESOLVED`
   - pending 候选的 active link 指向已删除案件：`FEISHU_ORPHAN_BINDING`
5. delete/bind/unbind/ignore/restore、pull、字段/明细显式处理共用 `FEISHU_WRITE_LOCK`，防止绑定生命周期与显式飞书写交错。
6. DTO/UI 明确显示活动孤儿为“本地案件已删除 / 绑定异常 / FEISHU_ORPHAN_BINDING”，仅保留可成功的“解除孤立绑定”；拉取归档后的孤儿不再进入 bound 列表，不渲染失效解绑按钮。partial run 与稳定错误码在最近运行和历史运行中均可见。
7. 最近 run 与候选 run 增加 `started_at DESC, rowid DESC` 稳定排序，避免同秒拉取误显示旧状态。
