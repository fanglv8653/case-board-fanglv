### 2.3 数据质量与流程观察

1. 事项编号 `P0000` 至 `P0016` 连续且无重复，17 条来源消息 ID 也均已填入；现有 `事项编号` 可以作为跨系统稳定业务键，不应再要求把历史编号改成 UUID。
2. 7 条已删除记录均保留删除请求时间和删除原因，其中包括系统验收残留、重复事项和客户不再办理等不同原因，证明“已删除”是可审计的软删除状态。
3. `关联案件` 以人工可读文本保存，存在“郑俊杰（舒孝保案）”“郑俊杰/杰鹏”等近似但不等价名称。案件看板不得按标题模糊匹配；首次映射或歧义时必须由用户选择案件，并把结果保存在本地同步账本。
4. `提醒次数` 全部为 0，`最后提醒时间`全部为空，说明提醒执行回写尚未真正运行；不能据此宣称已有可靠提醒闭环。
5. 表内还存在 1 条资料、1 条备忘。同步到“待办事项”模块后应保留类型并允许筛选；资料/备忘默认不进入“未完成待办”计数，也不自动复制为案件进展。
6. 当前样本只有 10 天、17 条，足以识别空字段和实际流程，但不足以永久否定未来的项目、归档、多人协作需求。因此字段删除应采取“先隐藏/停用，验收后再删”的可恢复顺序。

## 3. 字段处置建议

### 3.1 保留并纳入 0.8.4 业务映射

`事项编号、事项、原始内容、类型、状态、优先级、截止时间、提醒时间、关联案件、下一步动作、标签、来源消息ID、来源时间、更新时间、完成时间、删除请求时间、删除原因`。

其中：

- `事项编号`作为远端稳定业务键，导入本地后保持不变；本地仍可使用内部 ID，但同步账本必须唯一保存该编号与飞书 record ID 的对应关系。
- `状态`沿用现有六值：收件箱、进行中、等待、完成、删除待确认、已删除；不得压缩为只有“待办/已完成”。
- `类型`沿用想法、待办、提醒、资料、备忘；0.8.4 首次同步不得因目前未出现“想法”而删除该合法选项。
- `截止时间`和`提醒时间`语义不同，分别映射；不得合并成模糊的“事项时间”。
- `关联案件`只作为显示和候选线索；真正绑定使用本地案件 ID，并需人工确认。

### 3.2 保留在飞书，但 0.8.4 暂不作为核心同步字段

| 字段 | 处理 |
| --- | --- |
| 信息强度 | 保留为 Hermes 解析元数据，案件看板默认隐藏，不参与待办排序、完成或案件绑定 |
| 提醒次数、最后提醒时间 | 作为未来提醒执行审计字段成组保留；0.8.4 未实现提醒回写前，不展示“已提醒”结论 |
| 关联项目 | 先在视图隐藏并停止同步；若一个完整验收周期仍无使用，再单独确认删除 |
| 外部归档路径 | 先在视图隐藏并停止同步；路径易失效且当前为空，后续若需附件应采用正式附件/链接模型 |

### 3.3 不建议现在新增的字段

不建议把原 N0 契约中的 `同步版本、基线哈希、内容哈希、删除状态`直接加入用户表：

- 版本、哈希、record ID、冲突状态属于同步实现细节，应保存在案件看板本地同步账本，避免污染已使用的收件箱。
- 当前 `状态 + 删除请求时间 + 删除原因`已经完整表达软删除，不应再造一个重复“删除状态”。
- 每次预演可从当前业务字段计算规范哈希，并与本地共同基线比较；不需要用户维护技术列。

### 3.4 建议新增的用户字段

本轮不建议强制新增用户可见字段。现有字段已能表达标题、正文、类型、优先级、时间、状态、来源和案件线索。若后续启用多人协作，再另行评估“负责人”；当前 17 条记录没有多人指派证据。

## 4. 对 v0.8.4 本地模型的必要修订

原 N0 契约是未读取真实表时形成的理想化 12 字段模型，不能直接实施。用户确认本报告后，主控应先修订契约，再开发：

1. `case_todos`增加或明确保存 `type、priority、next_action、remind_at`；`content`映射原始内容，`item_at`不能再混合截止时间与提醒时间。
2. 本地状态不能只用 `done`表达全部远端状态；应增加明确的业务状态字段，并为旧 `done/done_at`保留兼容投影。
3. 同步账本保存飞书 record ID、事项编号、共同基线哈希、最近远端/本地哈希、冲突及案件映射；不要求远端新增技术列。
4. 首次导入保留全部 17 条，包括已删除记录；默认 UI 只显示有效记录，回收站可查历史，避免丢失删除原因与去重证据。
5. 同步范围覆盖五类记录，但首页“未完成待办”统计默认只计入类型为待办/提醒且状态为收件箱、进行中或等待的记录。
6. 复制到案件进展继续保持人工触发；资料、备忘和想法不得默认复制，必须由用户显式确认。

## 5. 建议的首次绑定流程

1. 冻结当前 Base rev 68 的只读快照和字段映射。
2. 在隔离飞书副本与临时 SQLite 上完成 schema、全量导入、幂等、冲突和软删除测试，不写正式表。
3. 对 8 条带“关联案件”的记录生成案件匹配候选；仅唯一精确结果可预选，仍由用户确认，歧义项不自动绑定。
4. 正式环境先执行只读预演，展示 17 条的新增/冲突/已删除分类及字段差异。
5. 用户在案件看板内确认后才写入本地；0.8.4 不后台自动写回飞书。
6. 字段结构修改另行单独确认；当前只建议隐藏两个空字段，不执行删除。

## 6. 本阶段结论与待确认项

建议采用以下决策：

- 接受“保持现有收件箱结构，最小改动绑定”的方向；
- `关联项目、外部归档路径`先隐藏/停用，不立即删除；
- `信息强度、提醒次数、最后提醒时间`保留为非核心元数据；
- 不向飞书新增同步技术列，版本/哈希/冲突全部放本地账本；
- 修订 0.8.4 本地数据模型以承接真实的类型、六态状态、优先级、截止时间、提醒时间和下一步动作；
- 经用户确认后，才进入契约修订和代码实现，不修改这张正式表的现有数据。
