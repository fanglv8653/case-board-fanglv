## 一、P0：统一生命周期协调协议

1. 在 `device_sync::feishu_binding_lifecycle` 中建立唯一的进程级生命周期锁实现。显式飞书动作和设备同步不再各自维护独立锁。
2. delete/bind/unbind/ignore/restore、pull、显式字段/明细处理均通过 `run_explicit_action`；后台与手动设备同步共同调用的生产入口 `device_sync::engine::sync_once` 通过 `run_device_sync_action`。
3. 设备同步冲突处理 `resolve_operation_conflicts` 也纳入同一协议，因为 `KeepRemote` 路径会经 `apply_upsert` 改写 `feishu_sync_links`。
4. 锁顺序固定为 `SYNC_RUN_LOCK -> BINDING_LIFECYCLE_LOCK`。显式飞书动作不获取 `SYNC_RUN_LOCK`，不存在反向获取或自锁环。
5. 占用时 fail-fast：显式动作返回稳定前缀 `FEISHU_WRITE_IN_PROGRESS`；设备同步返回稳定、脱敏、可重试的 `SYNC_FEISHU_LIFECYCLE_BUSY`。调度器将其作为稍后重试状态处理，不继续 apply，也不改变既有暂停/成功语义。

## 二、P0 并发反例证据

测试 `feishu_binding_lifecycle_tests::r2_barriers_cross_explicit_device_sync_and_lifecycle_production_entries` 使用 multi-thread Tokio、Barrier 与受控 oneshot，穿过真实生产协调入口：

1. 显式动作持锁并暂停时，真实 `engine::sync_once` 返回 `SYNC_FEISHU_LIFECYCLE_BUSY`；冲突处理入口返回相同稳定码；生命周期删除闭包进入次数为 0，案件未被删除。
2. 设备同步经 `sync_once_with_entry_gate_for_test` 在取得生产共享锁后暂停时，显式动作闭包进入次数为 0，并返回 `FEISHU_WRITE_IN_PROGRESS`。
3. 释放 barrier 后各自正常退出，证明不是永久锁死；设备同步继续到既有 `SYNC_NOT_FOUND` 业务结果。

## 三、P1：active orphan 缺 inbox 本地恢复

1. `unbind_case` 在同一事务内先确认案件是否仍存在。只有 active orphan 可用 `INSERT OR IGNORE` 合成受抑制恢复 inbox；正常案件的 active link 缺 inbox 仍返回 `FEISHU_BINDING_NOT_FOUND`，状态指纹不变。
2. orphan 恢复继续复用统一隔离逻辑：字段候选设为 `superseded`，明细候选设为 `superseded`，冲突设为 `dismissed`，link 归档，inbox 恢复为 `pending_binding / bound_case_id=NULL / resolved_at=NULL / auto_bind_suppressed=1`，审计写入 `previous_case_id=NULL`。
3. 数据库回归确认 `PRAGMA foreign_key_check` 为空；生产 HTTP spy 确认 read/write 为 `0/0`；解绑后不再出现在 bound preview。
4. UI 契约回归确认 active orphan 仍显示唯一可成功的“解除孤立绑定”，且后端源码存在仅 orphan 可触发的恢复分支。
