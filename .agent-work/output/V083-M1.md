# V083-M1｜数据库迁移谱系与启动恢复实现报告

状态：`accepted`（主控 2026-08-07 验收；历史 checksum 自动兼容为 `pending_verified_input`）

## 一、结论

已实现“sidecar 文件门禁 → 无 sidecar 主库 immutable 只读预检 → 稳定分类 → sqlx migrate”流程。任何 WAL/SHM sidecar、未知 checksum、未知已应用版本、失败迁移行、迁移历史缺失/为空但存在用户 schema，或已应用迁移的 schema sentinel 缺失，都会在创建 read-write/WAL pool 前失败关闭。

当前没有取得笔记本真实旧 checksum。第二轮修订已直接移除预留 allowlist、checksum 更新计划和 CAS 写动作；所有 checksum mismatch 均返回 `DB_MIGRATION_CHECKSUM_UNKNOWN`。没有猜测历史值，也没有保留原先的任意 checksum 改写或 `set_ignore_missing(true)`。

Tauri setup 已接入现有 `rfd::MessageDialog` 原生提示。兼容性失败时提示错误码、数据库位置、备份建议和退出说明；用户关闭提示后进程直接退出，不再落入 setup `.expect()` 的 panic 路径。

### 首轮退回修订

主控首轮静态验收指出：原实现对“没有 `_sqlx_migrations`”无条件放行，可能让已有用户 schema/业务数据但迁移历史丢失的未知库进入 RW/WAL 与 migrate。现已修订为：

- 缺少迁移表时，继续只读检查 `sqlite_master`；只有零用户对象的真正空 schema 才放行；
- 存在任一非 SQLite 内部 `table/view/trigger/index` 时，返回 `DB_MIGRATION_LINEAGE_INCOMPATIBLE`，`reason=migration_history_missing_for_existing_schema`；
- `sqlite_master`、`PRAGMA table_info`、`PRAGMA foreign_key_list` 查询或字段解码失败统一返回结构化 `DB_MIGRATION_LINEAGE_INCOMPATIBLE`，`reason=schema_metadata_unreadable`，由 setup 进入原生恢复提示；
- 新增未知既有 schema + 合成业务行夹具，失败前后同时比较逻辑与 DB/WAL/SHM 物理指纹。

### 第二轮退回修订

独立审计指出“空迁移历史表绕过”和普通 `read_only(true)` 可能创建/重建 sidecar 的 P0 缺口。修订及证据如下：

- `_sqlx_migrations` 存在但 0 行时，继续检查其他用户对象；有任一其他用户 schema/业务表即返回 `migration_history_empty_for_existing_schema`；
- 本地 sqlx-sqlite 0.8.6 源码确认 `.immutable(true)` 仅向 SQLite URI 加 `immutable=true`；项目 bundled libsqlite3-sys 0.30.1 对应 SQLite 3.46.0；
- 隔离实验使用 SQLite 3.53.1 构造“提交内容仅在 WAL”的完整 sidecar 与缺 SHM 副本。`mode=ro&immutable=1` 两种均保持文件不变但看不到 WAL 内表，证明 immutable 不能用于读取未 checkpoint WAL；`locking_mode=EXCLUSIVE` 只读实验返回磁盘 I/O 错误，也未采用；
- 因此冻结保守边界：主库旁 `-wal` 或 `-shm` 任一存在（或存在性无法安全确认），在首次 SQLite 连接前返回 `wal_sidecar_present_requires_recovery`；不自动删除、创建、重建、打开或 checkpoint sidecar；
- 只有 sidecar 均不存在时，才使用 `read_only(true)+immutable(true)+create_if_missing(false)` 查询已 checkpoint 主库；关闭后再次检查 sidecar；
- 新增完整 DB+WAL+SHM、缺 SHM、仅 SHM 三种合成形状；被测冻结目标的物理基线在任何 SQLite helper 前采集，`init_pool()` 返回后也先采物理结果，再进行其他断言；
- 组合异常优先级显式冻结为“失败行/未知版本/history gap → sentinel 缺失 → checksum unknown”，并增加 sentinel + checksum 组合夹具；
- 移除整个 checksum allowlist/更新计划/CAS 执行框架；未来取得真实 checksum 后须另开经审计实现，不得直接恢复当前删除的框架。

实验异常退出曾遗留一个 `.agent-work/threads/worker-m1/immutable-wal-proof-*` 临时目录；已解析并确认绝对路径位于本线程目录、Python 进程退出无占用后精确删除，复核 `remaining=0`。

核验依据：SQLite 官方 [WAL 只读条件与 sidecar 持久状态](https://www.sqlite.org/wal.html#readonly)、[URI immutable 语义](https://www.sqlite.org/uri.html#uriimmutable)，以及本机 `sqlx-sqlite-0.8.6/src/options/mod.rs`、`connection/establish.rs` 和 bundled `libsqlite3-sys-0.30.1/sqlite3/sqlite3.c`。Python 实验只用于否证“immutable 必然读取 WAL”，生产安全边界不依赖 Python 与 bundled SQLite 版本一致：只要 sidecar 存在即不打开 SQLite。

## 三、写前只读不变量

### 既有文件库

1. `init_pool()` 先判断数据库文件是否已经存在；
2. 用文件 API 检查同路径 `-wal`、`-shm`；任一存在或无法确认不存在即结构化失败，不建立 SQLite 连接；
3. sidecar 均不存在时，只建立单连接 `read_only(true)+immutable(true)` pool，设置 `create_if_missing(false)`，不设置 WAL；
4. 只查询 `_sqlx_migrations`、`sqlite_master`、`PRAGMA table_info`、`PRAGMA foreign_key_list`；迁移表缺失或为空时额外确认不存在其他非 SQLite 内部用户对象；
5. 只读 pool 完成检查并关闭，再次检查 sidecar；
6. 只有预检通过，才创建原有 read-write/WAL pool；
7. 不存在 checksum 写动作；再由默认 `ignore_missing=false` 的 sqlx migrator 执行正常升级。

### 全新库

- `:memory:`、路径不存在的库直接进入正常创建和迁移；
- 已存在但没有 `_sqlx_migrations` 的 SQLite 文件，只有经只读确认不存在任何用户 `table/view/trigger/index` 时才允许正常迁移；
- 已有用户 schema 但迁移历史丢失的文件失败关闭，不进入 RW/WAL pool；
- 已有用户 schema 但 `_sqlx_migrations` 为 0 行的文件同样失败关闭；
- 正常关闭、无 sidecar 的 0.8.2 库可进入只读谱系预检；任何 sidecar 形状必须先原样备份，并只在隔离副本上受控 checkpoint/恢复；
- 不自动删除、覆盖、重命名或重建异常数据库。

### 失败路径指纹

失败夹具均在调用 `init_pool()` 前后比较：

- `_sqlx_migrations` 全部元数据行；
- `sqlite_master` 的类型、名称、所属表和完整建表 SQL；
- 合成 `cases` 业务标记行；
- 数据库文件完整字节；
- `-wal`、`-shm` 的存在状态及完整字节。

其中未知既有 schema 夹具比较其完整 `sqlite_master` 与 `legacy_cases` 合成业务行；具有迁移历史的夹具比较完整迁移行、schema 和 `cases` 合成标记。只有对应逻辑和物理指纹全部相同，测试才通过。

## 五、checksum 写动作已禁用

生产代码中不再存在 `MigrationCompatibilityRule`、`MIGRATION_COMPATIBILITY_ALLOWLIST`、`MigrationPreflightPlan`、`ApprovedChecksumUpdate` 或 `apply_approved_compatibility_actions`。已知版本 checksum 不等于当前嵌入值时直接返回 `checksum_not_allowlisted`，没有进入 RW pool 后修改 `_sqlx_migrations` 的路径。笔记本真实旧 checksum 仍为 `pending_verified_input`；取得来源核验值后也必须另开安全设计与审计，不能在本版本内临时加入写规则。

## 十、范围事故与恢复证据

实现中曾误执行：


由于 `lib.rs` 是 crate root，rustfmt 默认递归处理其 `mod` 子模块，造成 161 个授权外 Rust 文件被格式/换行触碰。发现后立即停止功能开发并向主控报告。

```text

M  src-tauri/src/db/mod.rs
M  src-tauri/src/lib.rs
```

主控已复核范围恢复通过并授权继续。后续只使用带 `skip_children=true` 的逐文件 rustfmt check；未再次递归格式化 crate root，未覆盖 N0 内容。
