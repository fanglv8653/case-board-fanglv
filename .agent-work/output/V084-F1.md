# V084-F1 交付报告

## 结论

已完成 0.8.4 待办事项与飞书多维表格“📥收件箱”的只读优先同步、三方差异预览和逐项人工处置。自动路径只读取飞书；写回必须由用户对单条候选显式确认。同步元数据全部保存在本地独立账本，不向现有多维表新增技术字段，也未在本任务中修改真实飞书数据。

## 绑定与字段契约

- 设置项独立保存 App Token、Table ID、View ID，可直接粘贴完整 Base URL 提取，未复用案件总表配置。
- 每次拉取先校验目标表名 `📥收件箱`、视图名 `收件箱`、22 个既有字段及关键字段类型/选项；结构漂移时失败关闭。
- 业务稳定键为既有 `事项编号`，同时隔离重复事项编号和重复来源消息 ID，不覆盖任一冲突记录。
- 空事项时间保持 JSON `null`；旧本地 `due_date` 仅在出站时按上海零点兼容投影，不回填 `item_at`，避免往返漂移。
- 来源字段保持不可变；程序创建而无外部消息 ID 的事项使用稳定 `caseboard:<todo_id>` 标识，避免重复创建。

## 同步语义

- 新增 0065 迁移，分别记录绑定基线、同步轮次、预览、冲突和逐次写操作审计；未继续扩张 `case_todos`。
- 拉取完整分页数据后计算 canonical JSON 和 SHA-256，以本地/远端/基线三方哈希判定 noop、拉取、推送、新建、冲突、软删除和远端缺失。
- 远端缺失不会自动删除本地事项；用户可选择在飞书重建，或二次确认本地软删除。
- 飞书内容只能在预览中逐项采纳；关联案件只显示候选并要求人工选择，远端人类可读案件文本不会直接写成本地 `case_id`。
- 本地写回飞书先复读远端并校验哈希，再串行写入并回读；写入结果无法确认时标记 `write_uncertain`，冻结候选且不推进同步基线。
- 未调用远端删除接口；“两边保留”会新建本地副本并将远端绑定迁移到副本，原本地事项保持独立。

## 已知边界

- 飞书公开的记录更新接口未显示可供本客户端使用的 ETag/revision 条件写参数，因此无法做到服务端原子 CAS。本实现采用写前复读、进程内串行、写后复读和不确定写冻结；同一记录被其他客户端在极窄窗口并发覆盖的风险仍需由冲突预览和人工复核承接。
- 本任务没有使用真实授权调用正式 Base，也没有导入现有 17 条记录；首次真实拉取必须由用户在 0.8.4 界面点击“生成同步预览”，确认候选后逐项采纳。
- 正式表既有字段内容未被自动清洗或批量改写；此前已确认的字段/视图调整是 N0 的独立外部操作，不计入 F1 实现结果。
- RC 阶段仍需完成整包构建、真实 UI 冒烟以及可正常启动 Rust 测试可执行文件环境中的数据库测试。
